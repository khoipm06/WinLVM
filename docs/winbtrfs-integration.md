# WinBtrfs Integration

WinLVM exposes LVM logical volumes as byte-exact Windows block devices. Btrfs filesystem support is delegated to maharmstone/WinBtrfs.

## Boundary

- WinLVM parses LVM metadata and exposes selected LVs.
- WinLVM does not parse or repair Btrfs.
- WinBtrfs mounts the exposed LV and owns filesystem semantics.

## Byte Layout Contract

LV byte 0 must appear as virtual device byte 0. Do not synthesize a partition table or add an offset unless a future explicit compatibility mode is requested.

This matters because Linux LVs commonly contain Btrfs directly at LV byte 0.

## Stable Device Identity

The virtual device identity is deterministic:

```text
Vendor: LVM2
Product: LogicalVolume
Serial: LVM-<VGUUID>-<LVUUID>
Instance ID: winlvm\<VGUUID>\<LVUUID>
```

This identity is generated by `make_virtual_device_identity()` and should be passed to the future kernel driver so Windows and WinBtrfs see stable devices across boots.

## Read-only v1 Flow

```text
lvm lvchange -ay --readonly vg/lv
  -> activation service validates metadata and mapping
  -> kernel driver exposes byte-exact virtual block device
  -> WinBtrfs mounts the Btrfs filesystem read-only
```

## Read/write v2 Requirements

Before writable Btrfs mounting is allowed:

- all backing PVs must be present;
- backing PV devices must be locked/offlined as far as Windows allows;
- write activation must be explicit and administrative;
- flush/FUA must propagate to every backing PV used by the LV;
- the kernel driver must reject unsupported mappings and overlapping writable activations.

## Unsupported Initially

- Btrfs multi-device setups inside one or more LVs;
- concurrent Linux/Windows ownership;
- write activation without explicit policy checks;
- metadata mutation as part of normal filesystem writes.
